# 产品版本与数据库升级规约

从 `1.0.0` 开始，产品版本由根 [VERSION](../../VERSION) 唯一确定，每版同时保存可读说明和机器校验的数据库目标。当前基线见 [1.0.0](1.0.0.md) 与[迁移台账](1.0.0.json)，决定依据见 [ADR-0013](../adr/ADR-0013-产品版本与数据库升级追溯.md)。本目录记录源码与升级合同；制品发布、环境迁移及人工验收要有各自证据。

## 版本号与维护源

使用稳定三段 `MAJOR.MINOR.PATCH`，当前机制不使用预发布后缀。

| 变化 | 示例 | 要求 |
| --- | --- | --- |
| 修复且保持公开合同、数据和升级兼容 | `1.0.0` → `1.0.1` | 可含兼容性修正迁移，说明旧程序能否继续运行 |
| 兼容新增功能 | `1.0.1` → `1.1.0` | 记录新增配置、迁移及默认关闭/回填规则 |
| 破坏公开合同或升级兼容性 | `1.1.0` → `2.0.0` | 先确认方案，明确迁移桥接、停机、数据及恢复路径 |

数据库是否变化不能单独决定升哪一段。产品版本、EF MigrationId、数据库引擎和第三方依赖是不同维度，不用一个数字代替全部状态。

| 位置 | 职责 |
| --- | --- |
| `VERSION` | 唯一产品版本；新任务先确定目标，封版后的修改先进入下一版本 |
| `Directory.Build.props` | .NET 工程从根版本读取程序集产品信息 |
| `scripts/product-version.cjs` | PC 构建读取根产品版本；模板 `frontend/PC/package.json` 的 `6.0.3` 继续表达来源元数据 |
| `desktop/package.json`、桌面锁文件 | 安装包需要的产品版本镜像，与 `VERSION` 一致，不成为独立维护源 |
| `docs/releases/<version>.md` | 该版功能、数据影响、来源/目标、步骤、恢复和已知限制，按 [TEMPLATE](TEMPLATE.md) 编写 |
| `docs/releases/<version>.json` | 有序完整迁移目标、历史迁移源文件 SHA-256 与中文摘要；新增封存，不覆盖旧版 |

版本说明区分开发中、源码基线已建立、制品已发布与环境已升级。校验通过只能证明覆盖到的源码/台账一致，不能替代发布批准或环境核验。

## 开发时必须完成

1. 定位当前 `VERSION`、上一版本说明和本次变更影响的调用方；确认目标版本及范围，大改动先在 Issue 或 PR 中确认方案。
2. 在版本说明与 PR 描述中写目标版本和数据库影响。涉及表列、索引/约束/注释、默认值、权限回填、JSON/历史数据转换、第三方存储都算数据库变更；没有变化写“无”，不要省略。
3. 串行生成归属 DbContext 的增量迁移和模型快照；已封版/已应用迁移及其 SQL helper 不删改、改名或重新压平，后续只追加修正。共享模型同时维护 PostgreSQL 和 SQLite，OAuth 组件独立维护。
4. 一次性数据修正优先复用 EF 链。确需独立脚本时先明确归属和版本顺序，在版本说明登记路径/摘要、前后条件、幂等/重入、事务/断点、数据核对和执行证据；不能出现不受版本链约束的临时生产 SQL，也不另建与 EF 竞争的历史记录。
5. 用获准的真实 Provider 验证新安装、上一支持版本代表性数据升级、再次执行无重复、失败保留/恢复；比较原字段、ID、凭据密文、历史、权限数据及新字段规则。只跑模拟或构建不能记为升级通过。
6. 完成开发及迁移生成后，更新版本说明并新建本版正式台账，补全所有 `TODO` 摘要，运行版本与仓库验证；不通过反复覆盖台账追赶尚未完成的开发。待实际交付时另保存不可变制品引用/摘要、升级证据及真实批准，不提前填写部署成功。

```sh
node scripts/verify.mjs --scope all
```

开源版本提供 `scripts/releases.mjs` 校验命令，仅校验版本、版本台账与迁移链（不包含内部变更记录，台账无 `changeRecord` 时跳过该字段）；新增版本时按下述要求手工维护 `docs/releases/<version>.md`、`<version>.json` 与 `VERSION`：先确定真实版本/日期，更新 `VERSION`、桌面 `package.json` 与锁文件的版本镜像，再创建版本说明与机器台账。已封台账的纠错通过后续版本或勘误记录解释，不重算旧摘要掩盖漂移。

台账覆盖每条链的全部有序 MigrationId，以及历史迁移 `.cs`、Designer 和 SQL helper 的 SHA-256；仅有新增迁移列表不足以判断旧库是否能升级。正常演进的 `*ModelSnapshot.cs` 不作为永不变化的冻结文件，模型一致性由 EF 及相应验证核对。台账未复制源码正文，不能代替源码或数据库备份。

摘要按原始文件字节计算；根 [.gitattributes](../../.gitattributes) 对三条迁移目录的 `.cs`/`.sql` 固定 LF 行尾，避免 Windows 检出自动转换触发误报。编辑器和归档工具也须保留 LF；本次不执行 Git 归一化或改写既有迁移来更新摘要。

JSON 的 `previousVersion` 关联上一个基线，`database` 固定包含 `postgresqlBusiness`、`postgresqlOAuth`、`sqlite`；每条链记录 `context/provider/directory/historyTable/migrations/files/changes`，`files` 为仓库相对路径到 SHA-256 的映射，`changes` 为本版新增迁移的中文摘要。本版某链无变更时 `changes=[]`，其完整 `migrations/files` 仍保留；可读版本说明同步写“无”。1.0.0 首次建基线时摘要覆盖全部既有迁移，这不表示本次重新执行了它们。

PC 构建把产品版本写入 HTML 的 `application-version` 元数据及 `__APP_VERSION__`，不增加页面布局。API/桌面 .NET 发布物携带 `VERSION` 与版本 JSON；桌面打包先运行版本校验，复用 PC 产物也核对其 HTML 产品版本，缺失或不符须重新构建。产物包含台账不代表该数据库已经应用目标迁移。

## 三条数据库版本链

| 执行顺序/适用产品 | Provider / DbContext | 历史表 | 边界 |
| --- | --- | --- | --- |
| 服务端第 1 步 | PostgreSQL / `OobDbContext` | `__EFMigrationsHistory` | 业务实体、Timescale 超表、业务数据修正 |
| 服务端第 2 步 | PostgreSQL / `McpOAuthDbContext` | `__McpOAuthMigrationsHistory` | OpenIddict 的四类组件存储，独立迁移目录 |
| 桌面独立执行 | SQLite / `SqliteOobDbContext` | `__EFMigrationsHistory` | 共享业务实体及 SQLite 类型转换，不应用 PostgreSQL/OAuth 链 |

前两条共享服务端目标数据库时，仍必须分别核对、串行执行并核对结果；前一条成功不代表两条已经原子完成。MCP 关闭也不能用功能开关代替目标版本的迁移登记。桌面本期不提供外部 OAuth，却仍维护共享 MCP 业务实体。

PostgreSQL 源码未固定 schema，部署必须按应用实际身份及连接的有效 SearchPath 查历史表和业务对象。不得只看默认 `public`、只看最新一条或只看迁移数量。未知迁移、缺口、顺序/摘要不符、目标库/schema 不符先停止核对，不伪造历史、跳过迁移或自动重建。已存在对象但没有正式迁移历史的库，需要单独确认接管方案。

PostgreSQL、TimescaleDB、SQLite 和 OpenIddict 的引擎/组件版本独立记录。TimescaleDB 扩展由获准的基础设施准备入口管理，业务初始迁移创建超表；引擎镜像版本与业务 schema 版本不能互相证明。第三方组件对象继续由其正式链拥有，不在业务迁移重复建同一对象。

## 已有系统升级步骤

当前采用短维护窗口；没有建立并验收多版本并行写入或零停机迁移能力。

1. 明确目标环境、应用身份、数据库/schema、当前产品和完整已应用迁移、目标版本/制品摘要、维护时段与执行授权。核对来源为受支持版本；更早的未版本化安装先与 [1.0.0 基线](1.0.0.md)逐条比对，不能按镜像 `1.0` 标签猜状态。
2. 停止旧应用实例及所有可能写入者，包括采集、邮件报表调度和维护任务；保留已核实的部署/进程信息。一个目标只允许一个迁移执行者。
3. 制作并核验可恢复的数据库备份，配套保留 Data Protection 密钥、获准私有配置、必要介质/意图文件及原程序制品。记录受保护备份位置和校验，恢复演练未做就如实登记。SQLite 必须使用一致性备份包含已提交 WAL，不能只复制运行中的 `.sqlite` 文件。
4. 核对升级 SQL、前置条件、数据回填及不可逆步骤，再按批准的明确目标应用增量。服务端先业务、再 OAuth；桌面使用现有管理员确认、先备份再升级的维护入口。服务端 `--initialize` 含账号/设备 Bootstrap，`db-init` 含权限/扩展准备，不能直接当作已有库纯迁移命令。本次未新增自动服务端升级执行器。
5. 核对完整迁移历史、待执行项、数据守恒/回填、约束及解密能力后，启动匹配版本。验证登录、权限、服务器/历史查询、实时通道及本版功能；健康检查和页面 HTTP200 不代表数据库已升级。默认禁用的服务/写开关不因迁移而自动启用。
6. 写环境交付记录：实际前后版本与迁移、schema、制品摘要、备份/恢复位置、执行时段、验证与遗留问题。日志、截图和私密备份留仓库外，公开记录仅保留脱敏指针；人工验收、非作者评审分别登记。

本规约只规定流程，不授予任何具体目标的数据库结构/数据写入、部署、秘密修改、删除或 Git 操作许可；仍遵守根授权边界。普通启动、页面挂载、健康检查和预检不得自动迁库、重建用户、导入设备或触发真机动作。

## 失败与回退

失败后保持停写并保留现场，核对已完成迁移和原执行状态；两条服务端链不能假设自动一起回滚，不以重新发送不同意图掩盖未知状态。仅在确认正式迁移可重入、前提仍成立后续跑。

程序降级前证明新结构/数据兼容旧程序；不能证明就按已批准恢复方案同时恢复升级前数据库、密钥/配置和对应制品。不默认执行 EF `Down` 或清表，特别是风扇历史归并等不可逆数据转换。恢复会失去快照之后写入的数据，升级记录必须说明恢复点和处理安排。新版本结构、密文、权限和外部副作用都要核对，不能只回退容器标签。

## 封版与制品

源码封版需版本一致、说明和台账完整、适用验证完成且限制已登记。完整版本标签（如 `1.0.1`）一经交付不覆盖；任何新的代码/迁移产生新版本。镜像、桌面包和数据库引擎制品各自保存内容摘要、架构和构建来源，安装按批准的不可变摘要定位。

历史镜像标签与交付记录不构成本版源码基线的唯一标识。本仓库不包含打包、签名、环境部署或恢复验收记录；实际发布时另附不可变制品摘要与验收证据，不修改旧版迁移台账。
