# ADR-0009：异常记录与业务结果分离

- 决策状态：接受；本系统采用该方案实施。
- 实施状态：已实施；自动整合验证与浏览器检查分别记录。
- 评审状态：已进行交叉代码检查；人工业务验收由使用方按自己的环境执行。

## 背景与备选

只写进程日志无法通过系统页面检索、复制故障，数据库故障时直接写同一业务 DbContext 又会漏记。用异常表示正常拒绝会混淆系统故障、电源发送结果和业务校验。

备选包括只写 ILogger、直接写异常表、独立外部日志服务。本期复用既有 PostgreSQL、IdService 和四层工程，以仓库外脱敏文件提供数据库故障期间的缓冲，无新框架或外部依赖。

## 决定

预期业务拒绝通过 ServiceResult / ApiResult 返回，驱动使用结构化结果，前端显式处理 success 分支。只有已识别的业务唯一约束竞争转换为 409，主键发号碰撞等仍进入真实异常边界。电源发送前明确未执行与发送后结果未知分别处理，日志失败不造成设备动作重试。

统一 IExceptionRecorder 接收受控上下文与实际 cause；原异常仅在后端内存中流转，驱动诊断不进入 JSON 合同。落盘前仅保留安全摘要、异常类型和脱敏代码帧，不保存原始 Message/Data/ToString、认证材料、请求正文或连接参数。同一异常引用去重；没有异常对象的真实设备失败也可结构化记录。

脱敏记录先以稳定 ID 追加至应用数据目录，再由独立短寿命 DbContext 持久化到普通表 OOB_SYSTEM_EXCEPTION。追加 checkpoint 在入库成功后推进；数据库失败短暂退避、恢复后补入，主键使重复回放幂等。日志模块自身错误不递归写回，不改变已保存样本、电源意图或业务结果。缓冲不自动删除；强杀、磁盘故障等不能承诺绝对零丢失。

管理员通过统一 API 分页查看和复制安全诊断。浏览器上报使用认证、CSRF、大小/频率约束，身份变化使旧队列失效；真实服务端类别和用户由服务端决定。正常业务拒绝、正常取消、停止和可选能力缺失不计系统异常。

## 兼容与恢复

追加一条授权 EF 迁移，只新增第九张普通业务表、中文注释和索引，不改既有时序数据。普通启动不迁库。发布失败时可停止新服务并恢复前版程序，既有业务表兼容；保留新增表与缓冲作为证据，不自动执行 Down 删除日志。数据库恢复后重放原记录，不生成新故障 ID。

## 验证依据

以真实隔离 Testing 库和 fake 驱动覆盖日志持久化、权限、脱敏、断库恢复、去重、HTTP/SignalR 边界、业务拒绝与主键碰撞分类。浏览器确认菜单、筛选、详情、复制与三语言；真机电源不纳入自动测试。
